# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Clawholics: a nail salon appointment system (booking, Xendit payments, loyalty stamps via QR scan, admin CMS). One Next.js 16 App Router app at the repo root, deployed to Vercel: Clerk auth, Supabase Postgres, Cloudflare R2 images, Resend emails, Tailwind v4.

## Commands

- `npm run dev` — `next dev` on :5174 (needs `.env.local`, see `.env.example`)
- `npm run build` — `next build` (includes the type-check); `npm run lint` — ESLint (`eslint-config-next`)
- `npm test` — Vitest (jsdom, `@` alias → `src/`); one pass: `npm test -- --run`; single file: `npx vitest run src/tests/contactUs.test.tsx`
- `npm run test:db` — Postgres integration tests in `src/tests/db` against a throwaway Docker Postgres
- `npm run db:export -- <dir>` — read-only export of the live D1 to JSON (wrangler login, root `wrangler.toml`); `npm run db:copy -- <dir> [--replace]` loads it into `DATABASE_URL` in one transaction (creates the schema if missing, refuses a non-empty target without `--replace`). Keep export folders outside the repo: they hold customer data.

## Architecture

### The old Worker is retired
The app runs only on its own route handlers and Supabase Postgres. The Cloudflare Worker `clawholics-api-staging` and its D1 database are no longer used: build everything for Next and Supabase, with no Worker fallbacks or compatibility paths. Its source (`worker-api/`), the Express `backend/` and the Vite `frontend/` were removed from the repo; see git history before the move to a single app. What's left of it in the code:
- `ported()` and `forwardToWorker` in `src/server/worker.ts`, and the `API_BACKEND` switch: the handlers only run when `API_BACKEND=next`, so it must be set to `next` in every environment (otherwise every request is forwarded to `API_PROXY_TARGET`).
- `wrangler.toml` and `db:export`/`db:copy`, the one-off D1 → Supabase data copy (`copy-from-d1.mjs` also backfills what D1 migrations 001–004 would have added).

### App structure
The app was ported from a Vite SPA (`frontend/`, now removed), which is why the screens use a react-router-style API.
- Every screen is written directly in its route's `page.tsx` under `src/app/` (`"use client"` files). Every page under `src/app/` is JSX only: imports, one call to its screen's hook (unpacking what it returns), and JSX with simple conditionals, `.map`s, class toggles and one-line handlers. State, effects, refs, other hooks, constants, computed values and helpers go in the screen's hook (`src/hooks/`, `hooks/admin/`, `hooks/client/`), `src/lib/` or a component; a page that needs a wrapper (`<Suspense>`, `OnboardingGate`) keeps its screen as a private function in the same file. The site pages' hooks include `useHomePage` (over `useHome` and `useTestimonials`), `usePrivacyPolicy` and `useTermsOfUse`; the client app's `useMyAppointments` and `useMyProfile`. The layouts keep only their server checks: the users.role lookup they share is `isApiAdmin` in `src/server/auth.ts`, the brand fonts are in `src/lib/fonts.ts` and the Clerk wording is `clerkLocalization` in `src/lib/clerkAppearance.ts`. `(site)/` screens render inside `SiteLayout`, with `OnboardingGate` where `App.tsx` had it (the service page `/services/[id]` wraps itself in it); the 404 screen is in `src/app/not-found.tsx`. `(admin)/` routes are the admin screens (kebab-case URLs such as `/admin-directory`; the old `/AS_*` URLs redirect in `next.config.ts`; each screen written directly in its route's `page.tsx` (a `"use client"` file; the Clients & Bookings page keeps its `<Suspense>` there), holding JSX only (see **Admin screens** below); `/admin` is the entry point and sends an admin to `/dashboard`, the admin landing page (business metrics from `GET /api/dashboard`, computed in `src/server/dashboard.ts`; the periods are in `src/lib/dashboardPeriods.ts`; the wins / watch-outs / suggestions banner is rule-based, in `src/lib/dashboardInsights.ts`); all three report pages share the period switch (`PeriodSwitch`: This week, This month, Last 30 days, Last 3 months, This year, All time; the Dashboard opens on This month too) and every number on them follows it, except the Dashboard's live lists (To act on, Active bookings). All time (`range=all`) runs from the first day on record to the last booking's day, a point per month, with an empty previous span, so its cards show no change pills (`compare`). The Dashboard opens with the salon at a glance (`dashboard/GlanceCards`, for the period against the one before: Total clients = client accounts with a visit confirmed and finished with Complete visit in it (a `visit_completions` row; status alone doesn't count), Total services and Artists = how many different ones were booked in it, Appointments = the visits finished with Complete visit in it, one each, walk-ins included; no links out), its Bookings over time chart (`bookingsTrend`, a bar pair per point of the period) and its Salon notes and Service mix (`overview` in the response, the period's; the notes are facts with no comparison, `lib/dashboardInsights.ts`). From 18 October 2026, by the visit's day (`TRACKER_FROM` in `server/dashboard.ts`), the Service mix, the glance cards' services and artists, the Salon notes' weekdays and artists, the bookings chart's Completed and the Sales page's Top services and How bookings ended (a booking marked Completed without it is left out) count only visits finished with Complete visit, by the day completed, while earlier visits still count by status; `/sales` and `/performance` show the rest of the same numbers (money cards, sales record; four key rates as stat cards (`dashboard/RateCards`: Cancellation rate, Booking conversion, Lead conversion, Repeat rate, each with a line of the rate so far in the period, `rateTrend` from `rateDayParts`; the money is only on the Sales page), artist utilization, Busiest weekdays (as many of the busiest days, spelled out, as Bookings per artist beside it has artists, so the two cards match; Monday to Sunday with none or seven or more, `busiestWeekdays` in `lib/dashboardFormat.ts`) and Bookings per artist), all three framed by `components/features/admin/dashboard/ReportPage.tsx`; every stat card on them has an ⓘ note saying what it is and how it's counted (`dashboard/StatInfoTip`, wording in `src/lib/dashboardInfo.ts`: update it when a number's rule changes); the money and visit counts come from the booking tracker: only visits an admin completed with Complete visit (a `visit_completions` row, so confirmed and completed) count, dated by the day completed (`tracked_d` in `server/dashboard.ts`): the glance cards' Total clients and Appointments, the Salon notes' returning clients (2+ such visits, a running count as of the period's end) and lapsed clients ("haven't visited in over 60 days", last such visit completed 60+ days ago), the Repeat rate, Revenue's and Gross income's balances, and the Sales record (five a page, each sale its downpayments + the balance recorded); the Sales page's Money row is for the salon's financial statements, from every paid downpayment (`DOWNPAYMENT_FLOWS`: dated by `payments.paid_at`, and by when it was earned, refunded (`appointments.refunded_at`) or forfeited by a cancellation or no-show (`cancelled_at`, the latest time it went into that state, also set when an unpaid hold runs out); older rows without those dates use the visit's day; a payment that arrived after its booking was cancelled is owed back, so it stays held until refunded): Gross income (downpayments paid + balances recorded at completion − refunds), Unearned income (downpayments held at the period's end, today at the latest, for visits not done yet: a liability), Forfeits & late fees (kept downpayments + `visit_completions.late_fee`) and Revenue (earned: the downpayments and balances of the visits completed in the period, the balance already holding the late fee, + kept downpayments; refunds have no card of their own, they come off Gross income); the admin layout is `noindex` and `src/app/robots.ts` disallows the admin paths). **Clients & Bookings** (`/clients`, `src/app/(admin)/clients/page.tsx`) is one screen: the client totals and every appointment with its client's details (`components/features/admin/bookings/AppointmentsTable.tsx`, drawn like the dashboard's bookings table: photo, email, phone, joined and last active from Clerk, visits counted from completed appointments; - **Data in the browser (TanStack Query):** every screen reads its data through TanStack Query (`QueryProvider` in the root layout, `makeQueryClient`: fresh for 60s, one retry); don't fetch in effects. The queries live in four places, by whose data it is:
  - `lib/publicQueries.ts` (`["public", …]`): what anyone may see (content, services, artists, FAQs, reviews, payment settings). The admin layout drops these on the way in (`ForgetPublicContent`). The `(site)` layout fills the shared ones on the server (`server/publicPrefetch.ts`, from `publicReads`, keys in `lib/publicKeys.ts` since the server can't import the browser fetchers) and passes them through a `HydrationBoundary`, so the prerendered pages hold the real content (`revalidate = 600`; an admin's save rebuilds them through the `catalog` tag). A read slower than 3s is left to the browser. The artists section's layout seeds every artist's gallery from one query (`publicReads.allNailistGalleries`), so the "Their art" strip doesn't ask once per artist.
  - `lib/accountQueries.ts` (`["account", clerkId, …]`): the signed-in client's profile (null without one), appointments and reviews. The onboarding gate, onboarding, profile, home and starting a booking share the one profile; after saving it, update the cached copy (`setQueryData`) before moving on, or the gate reads the old one.
  - `lib/bookingQueries.ts` (`["booking", …]`): an artist's hours, days off and taken times, read through `hooks/useArtistAvailability.ts` by booking, reschedule and the walk-in form (full days from one `slots-range` request); the artist editor's Day Off card reads the shown month's `bookedRange` for its booked days, and `adminDataChanged` refreshes the taken times too; the checks before booking ask again with `fetchTakenTimes` (staleTime 0). Also dropped by the admin layout.
  - `lib/adminQueries.ts` (`["admin", …]`): the admin screens' data. After an admin changes an appointment or a client's stamps, call `adminDataChanged(queryClient)`: it refreshes what shows them (lists, schedule, dashboard, client pages, proofs, leads) but not the Clerk-backed directory, which `directoryChanged` refreshes after an admin account changes. Content editors start their forms from `hooks/admin/useEditorSource.ts` (fetched again on every open), and forms fill through `hooks/admin/useFillForm.ts`, only while nothing is unsaved.
  - `QueryProvider` drops the account and admin queries when the signed-in user changes.
- `src/lib/router.tsx` re-creates the react-router API the screens use (`Link`, `useNavigate`, `useLocation`, `useParams`, `useSearchParams`, `Navigate`) on `next/navigation`. Router `state` is kept in sessionStorage per target path (cleared on a fresh page load, kept on reload) and is null during server render/hydration, so screens that need it on first render (booking, payment, reschedule, profile) are wrapped in `components/guards/ClientOnly` in their `page.tsx`. Screens using `useSearchParams` need a `<Suspense>` there too.
- With `NEXT_PUBLIC_API_BASE_URL=/api`, the browser stays same-origin and every `/api` path is answered by a route file under `src/app/api/`. The `fallback` rewrite in `next.config.ts` (to `API_PROXY_TARGET`, the old Worker) is left over from the migration and only applies when that variable is set.
- SVGs import as React components via `@svgr/webpack`; static image imports are `StaticImageData`, so use `.src`.

  - **Directory profiles (new, no Worker equivalent):** GET `/directory/profiles`, admin only (`src/server/handlers/directoryProfiles.ts`): each Clerk user's uploaded photo, join date and last sign-in by Clerk id, for the directory cards (`/directory` keeps the Worker's columns). A Clerk failure answers `{ profiles: {} }` and the cards show initials.
  - **Handlers:** the 2B and 2C handlers live in `src/server/handlers/`, and the route files under `src/app/api/` only map URLs, including the Worker's alias paths, to them.
- **Access rules (stricter than the Worker):** the ported routes don't copy the Worker's open access. Access comes from the verified session:
  - **Owner or admin:** appointment by id, payment details, payment create, reschedule and refund.
  - **Owner only:** proof upload, and reviewing a visit.
  - **Admin only:** the appointment list, status changes, admin booking, the schedule, proof review and the payment settings PUT. Also every CMS/catalog write (including `/gallery/:id`, which the Worker left open), the directory, the admin list and promote-admin, `/users/stamps`, `/users/scan/*` and the scan history. `POST /upload/image` is admin only too (clients upload through the proof and review endpoints), and only into the admin screens' folders.
  - **Uploads** (that route, the About image, payment proofs, review photos) check the file's first bytes against the real JPG/PNG/WEBP signature (`server/imageFiles.ts`), not just the type the browser claims.
  - **Rate limits** (`server/rateLimit.ts`, checked by `ported()` before the handler): 300 requests a minute per visitor, and stricter limits on the contact form, booking, payment creation, proof and review uploads and image uploads; the Xendit webhook and the cron run are exempt. Counted in each server instance's memory (best effort); the Vercel Firewall's rate limit rule is what holds across instances. Off under the test runner.
  - **Security headers** (`next.config.ts`): HSTS, `frame-ancestors 'self'` with X-Frame-Options (only the admin's preview frames the site), `nosniff`, a strict referrer policy and a Permissions-Policy allowing only the camera (the scanner); no X-Powered-By. Scripts, styles and images aren't restricted by the CSP (Clerk, Xendit, Maps and Fonts load from their own domains, and Next's inline scripts would need nonces).
  - **Signed-in user's own:** `/users/profile` and `/users/redeem` use the session's user, not the `clerk_id` param; `/users/appointments` and `/users/clerk/:id` are owner or admin.
  - **`/emails`:** answers `{ success: true }` without sending. The confirmation emails go out on the server when a payment is confirmed; the Worker's route emailed whatever it was sent.
  - **Booking create:** uses the session's user, not `user_id` from the body, and the catalog's service and artist names, not the body's.
  - **Booked times** (`server/slotRules.ts`, `checkSlot`, used by booking, walk-ins and reschedule): a real date, one of the artist's `nailist_time_slots`, not a day off, not overlapping a held booking, and not started or starting sooner than the notice (`booking_min_notice_hours`; walk-ins and admins' moves may be); stored as `HH:MM-HH:MM`. A client reschedules only a `CONFIRMED` booking 72+ hours ahead and cancels only a booking still to happen (`PENDING`, `AWAITING_PROOF`, `CONFIRMED`) that hasn't started; an admin reschedules or cancels any booking still to happen. The status PATCH accepts only the known statuses.
  - **Xendit invoices** stay open for the booking's remaining hold plus 2 minutes, and only a `PENDING` booking can be paid. The webhook applies a payment once (a repeat changes nothing) and moves only a `PENDING` or `CANCELLED` booking; a payment it can't apply (slot taken since, or already paid, refunded…) notifies the admins (`payment_to_check`) to refund it.
  - **Xendit webhook:** must carry `x-callback-token` equal to `XENDIT_CALLBACK_TOKEN`, or it's refused.
- **A booking paid online is confirmed by the payment:** when the Xendit webhook marks a `PENDING` booking's invoice paid it goes straight to `CONFIRMED`, the client gets the confirmation email (`sendAppointmentConfirmation`) and the admins a `booking_paid` notification ("New booking paid", linking to the client's page). There's no `AWAITING_CONFIRMATION` status any more (migration `20261028000000_confirm_paid_bookings.sql` confirmed the ones left) and no screenshot upload for it: the confirmation step `/my/confirmation` asks the client to send their payment screenshot to the salon's Instagram (`instagramUrl` in `lib/socialLinkData.ts`: the saved Instagram social link, else `DEFAULT_INSTAGRAM_URL`). Payment proofs (`payment_proofs`) remain only for paying by proof: `POST /payment/proofs` takes a `PENDING` booking while MANUAL is on, and approving the proof confirms it (with a MANUAL payment row). "Proofs to review" is any booking whose latest proof is pending (`PROOF_TO_REVIEW_SQL`, `server/proofRules.ts`); Clients & Bookings has a Proof column (`bookings/ProofThumb.tsx`).
- **Emails** (`src/server/email.ts`) HTML-escape every value and are sent after the response with `after()` (`inBackground` in `src/server/http.ts`).
- **Server modules:** `src/server/` holds the server-only code (`import "server-only"`):
  - `db.ts`: postgres.js on `DATABASE_URL`, the Supabase transaction pooler, `prepare: false`. Connections can die silently (e.g. after a laptop sleep), leaving every query queued forever, so `ported()` checks a request still waiting after 10s with `sqlResponds()`: if the connections don't answer, `resetSql()` replaces the client (only the one found dead). Either way a GET runs once more (a single connection can die while the rest still work) and the first answer wins; a GET whose connection broke under it (`CONNECTION_DESTROYED` etc.) also runs once more. Writes are never re-run. These limits count working time, not wall time (`src/server/loopTimer.ts`): the dev server blocks its event loop while compiling routes or compacting its cache (20-50s), and plain timers then fired before the database answers already waiting were read, which looked like dead connections and set off needless resets. Connections live at most 60s. `resetSql()` gives the old connections a few seconds to close instead of cutting them at once: Supabase's pooler counts a connection cut during login as a failed login and, after several, refuses every new connection for about two minutes (`ECIRCUITBREAKER`). A stall also logs when the server itself was frozen for most of it, and the Schedule asks once more after a 503. A stalled request also logs the database's own activity (`logDatabaseActivity`, over a separate one-off connection) to show whether it was busy, blocked on a lock, or not reached at all. The Clerk directory sync (`syncAllUsersFromClerk`, started by every `GET /directory`) runs one at a time and at most every two minutes. Anything unanswered at 30s gets a 503. Values go in as template parameters. Without prepared statements, array parameters aren't typed, so build `OR` fragments instead. The clients run with `fetch_types: false` (no `pg_type` lookup on every new connection), so a Postgres array comes back as a raw `'{…}'` string: return lists as json (`json_agg`, `to_json(array_agg(…))`), never as an array.
  - `auth.ts`: the Clerk-verified requester, with roles from `users.role`. The `clerk_id` header is never trusted.
  - `r2.ts`: R2 through the S3 API.
  - `catalog.ts`: the read queries.
  - `publicCache.ts`: the public catalog/CMS reads cached with `unstable_cache` under one `catalog` tag (admins' reads skip it). Every admin write to those tables must be wrapped in `changesCatalog()`, which drops the cache on success; anything else shows within an hour.
  - `clerkSync.ts`: directory sync with Clerk (names, `publicMetadata.role`, deletes). Clerk errors are logged, never fail the request.
- **Response shapes:** the ported endpoints answer with the Worker's shapes (columns, order, number types), which the frontend relies on; keep them when changing a query, and cast `count(*)` to `int`.
- **Schema and seed:** the schema is in `supabase/migrations/` and is the D1 schema translated: same columns, 0/1 integer flags, text dates and times, RLS on with no policies. Schema changes are new files in `supabase/migrations/`; when they reach `main`, `.github/workflows/migrations.yml` applies them to production with `supabase db push` (secret `SUPABASE_DB_URL`, the session pooler on port 5432). It refuses to start if the database has the schema but no migration history: record what's applied with `supabase migration repair --status applied <version>...` first. It can also be run by hand from the Actions tab, as a dry run by default. `supabase/seed.sql` is dev/test data, edited by hand (its old generator read the removed `database/init.sql`); never load it into production.
- **Tests:** `npm run test:db` runs `src/tests/db` against a throwaway Docker Postgres. The files run one at a time, since each rebuilds the schema through `testDatabase.ts`. Plain `npm test` skips those tests. `.github/workflows/ci.yml` runs on every PR and push to `main`: the unit tests (30s per test, since jsdom screens are slow on a shared runner; the type-check is left to Vercel's build), the `src/tests/db` tests against a Postgres service container, and lint (errors fail it; the warnings don't).
