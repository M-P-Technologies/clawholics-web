# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Clawholics: a nail salon appointment system (booking, Xendit payments, loyalty stamps via QR scan, admin CMS). One Next.js 16 App Router app at the repo root, deployed to Vercel: Clerk auth, Supabase Postgres, Cloudflare R2 images, Resend emails, Tailwind v4.

## Commands

- `npm run dev` — `next dev` on :5174 (needs `.env.local`, see `.env.example`)
- `npm run build` — `next build` (includes the type-check); `npm run lint` — ESLint (`eslint-config-next`)
- `npm test` — Vitest (jsdom, `@` alias → `src/`); one pass: `npm test -- --run`; single file: `npx vitest run src/tests/contactUs.test.tsx`
- `npm run test:db` — Postgres integration tests in `src/tests/db` against a throwaway Docker Postgres
- `npm run db:export -- <dir>` — read-only export of the live D1 to JSON (wrangler login, root `wrangler.toml`); `npm run db:copy -- <dir> [--replace]` loads it into `DATABASE_URL` in one transaction (creates the schema if missing, refuses a non-empty target without `--replace`). Keep export folders outside the repo: they hold customer data.

## Architecture

### Legacy Worker (still live until cutover)
Production data is still in Cloudflare D1, served by the Worker `clawholics-api-staging` (https://clawholicsbymax.com). Its source (`worker-api/`), the Express `backend/` and the Vite `frontend/` were removed from the repo; see git history before the move to a single app. `wrangler.toml` is kept only for the D1/R2 bindings that `db:export` uses, so `wrangler deploy` no longer works from here. The live D1 has only its baseline migration; `copy-from-d1.mjs` backfills what D1 migrations 001–004 would add (categories, service position and pricing mode, contact fields, payment settings).

### App structure
The app was ported from a Vite SPA (`frontend/`, now removed), which is why the screens use a react-router-style API.
- `src/app/` holds only thin route files. `(site)/` routes render a screen from `src/views/` (the old `src/pages/`, renamed because Next reserves `pages/`) inside `SiteLayout`, with `OnboardingGate` where `App.tsx` had it. `(admin)/` routes are the admin screens (kebab-case URLs such as `/admin-directory`; the old `/AS_*` URLs redirect in `next.config.ts`; screens in `src/admin/`, grouped like the sidebar into `overview/`, `front-desk/` and `content-management/`, and holding JSX only (see **Admin screens** below); `/admin` is the entry point and sends an admin to `/dashboard`, the admin landing page (business metrics from `GET /api/dashboard`, computed in `src/server/dashboard.ts`; the periods are in `src/lib/dashboardPeriods.ts`; the wins / watch-outs / suggestions banner is rule-based, in `src/lib/dashboardInsights.ts`); `/sales` and `/performance` show the rest of the same numbers (money cards, sales record; key rates, artist utilization), all three framed by `components/admin/dashboard/ReportPage.tsx`; its Money row is worked out from list prices and downpayments only: balance paid at the salon, confirmed visits booked ahead, and what cancellations cost; the admin layout is `noindex` and `src/app/robots.ts` disallows the admin paths). **Clients & Bookings** (`/clients`, `src/admin/front-desk/ClientDirectory.tsx`) is one screen: the client totals and every appointment with its client's details (`components/admin/AppointmentsTable.tsx`, drawn like the dashboard's bookings table: photo, email, phone, joined and last active from Clerk, visits counted from completed appointments; the name opens the client page; status changed in the row; Manage opens the client page, and a "Proof to review" badge opens the details drawer for the review; `?status=` opens on a status). There's no separate client list any more; `?view=leads` (the dashboard's warm leads) adds a list of those clients, who have no appointments yet; the old `/client-directory` and `/appointments` redirect there with their query. The sidebar's "Front Desk" section holds it, Schedule, the Admin Scanner and the Admin Directory; only the sidebar's menu scrolls (scrollbar on the left, `.sidebar-scroll`), with the logo and Log out fixed, and it collapses to an icon rail (`NAV_ICONS` in `SideBar.tsx`; the choice is kept in localStorage). An appointment's details open in a drawer from the right (`AppointmentDetailsModal`, used by Clients & Bookings and the Schedule). On phones the admin has a bottom tab bar (`components/admin/AdminTabBar.tsx`, rendered by `SideBar`; the routes are in `adminNav.ts`: Dashboard, Bookings, Schedule, Scanner), and the daily screens (Clients & Bookings, Schedule, Scanner) use `AdminShell` and show phone layouts below `lg`; from `lg` up the sidebar and the old layouts apply; below `md` the admin tables (directory, appointments, bookings, sales record, artist utilization, client appointments) show each row as a card, five to a page (`components/admin/RowCards.tsx`, switched by `useTableLayout` in `hooks/useMinWidth.ts`, which is true on the server and without `matchMedia`, so tests see tables); and `(admin)/layout.tsx` checks on the server that the Clerk user has `publicMetadata.role === "admin"` (replaces `AdminRoute`). `src/proxy.ts` is Next 16's middleware and only runs `clerkMiddleware`.
- **Home page and footer words** are editable in Admin > Homepage (`src/lib/homeSections.ts`): the hero line, studio intro (with an optional photo replacing the emblem), the four "Why choose us?" cards (each an icon from `FEATURE_ICONS`, a title, text and a page from `SITE_LINKS`), the service photo strip (`home_strip`, JSON slides of a service with an optional title and photo; empty shows every service with a photo), the About teaser, the FAQ heading, the closing banner and the footer (column titles, chat button, logo, copyright). They're `home_*` content keys; a key never saved falls back to `HOME_TEXT_DEFAULTS`/`DEFAULT_FEATURES`, so the site reads the same until edited. The Quick contact's Good to know list is `about_good_to_know` (one item per line), edited in About Us. The salon's address and map link are About Us's `about_location`/`about_location_url`; the Contact page and booking take them through `withSalonLocation` (the old `contact_location` keys are only a fallback). Social links are one list, `social_links` (JSON, `src/lib/socialLinks.tsx`, edited in Contact Us with a platform icon each); until it's saved the old fixed `social_{facebook,instagram,tiktok}_*` keys are shown. The Services page's words (its heading `home_services_title`, subtitle `home_services_subtitle` and closing banner `home_services_cta_*`, see `SERVICES_PAGE_DEFAULTS`) are edited and saved in Admin > Services; the Homepage editor never sends them. Banner buttons open a page of the site or a full web address (`LinkField`, `ctaLink`). The FAQ page's heading, intro and closing banner are `home_faq_page_*`/`home_faq_cta_*` (`FAQ_PAGE_DEFAULTS`), edited in Admin > FAQs. List editors keep their page's words with `hooks/admin/usePageWords.ts` (load, Save bar, check, save only those keys). The Artists page's heading, intro and "Their art" title are `team_title`, `team_description` and `team_art_title` (`TEAM_PAGE_DEFAULTS`), edited in Admin > Artists and saved with `PUT /content/team`. The carousel (`/carousel`) is the About page's studio gallery and is edited in About Us; the Artists page's "Their art" strip shows the artists' own gallery photos (`hooks/usePhotoStrip.ts`, taken in turns across artists).
- **Site theme:** Admin > Homepage's Look section picks a colour set and the display, script and body fonts (`src/lib/siteTheme.ts`, saved as `home_theme_*`). `hooks/useSiteTheme.ts` (in `SiteLayout`) sets the brand colour variables and re-points `--font-gloock`, `--font-luxurious-script` and `--font-noto-sans` on `<html>` for the public site only; the other twelve fonts aren't built in (next/font downloads every font at build time, and twelve at once timed out): `hooks/useGoogleFonts.ts` adds a Google Fonts stylesheet in the browser, for just the chosen fonts on the site and for all of them in the picker.
- **Admin screens** (`src/admin/`) are JSX only: no state, effects, constants or helpers. Each screen's state, loading and actions are in a hook in `src/hooks/admin/` (`useClientPage`, `useClientDirectory`, `useAdminDirectory`, `useAdminScanner`, `useSchedule`, `useReports`, and one `use…Editor` per content editor; FAQs and Terms share `useOrderedItems`); its constants and pure helpers are in `src/lib/admin/` (`clientPage.ts`, `schedule.ts`, `cmsPages.ts`, `aboutEditor.ts`, `contactEditor.ts`, `homeEditor.ts`); its fetches are in `src/services/`; and its own sub-components are in `src/components/admin/` (`client/`, `schedule/`, `scanner/`, `cms/StripEditor.tsx`, `EditAdminModal.tsx`, `FeedbackModal.tsx`). Keep new admin code in those places. A hook's returned object mustn't be passed to a `ref` prop directly (destructure the ref callback first), or `react-hooks/refs` flags every read of it.
- **Admin top bar** (`components/admin/AdminTopBar.tsx`, drawn by `AdminShell` on every admin screen): the greeting, the screen's title and its own controls on the left; today's date, a View site link and the signed-in admin (`hooks/admin/useAdminAccount.ts`) on the right. On phones it shows the title, the controls and the admin's avatar only.
- **Client page** (`/clients/[id]`): a profile panel and a tabbed panel (Overview with the counts and a booking tracker from `src/lib/bookingTracker.ts`; Notes & next steps; Appointments), each 80vh tall on a computer. `GET /clients/:id` adds each appointment's `booked_at`, latest proof (`proof_sent_at`, `proof_status`, `proof_reviewed_at`) and `payment_status` for the tracker, and the client's review of the visit (`review_rating`, `review_comment`, `review_photo_url`), shown in the Appointments tab's Review and Review photo columns. The last and next visit dates are in the profile panel's Client info. Client info also shows the client's birthday (`customer_profiles.dob`) and the optional contact details they fill in on their profile's Edit details sheet (other phone, Instagram, Facebook, preferred contact method; fields in `src/data/profile.ts`, saved by `PUT /users/profile`).
- **FAQs** show on their own page, `/faq` (`views/site/Faq.tsx`, `hooks/useFaqs.ts`), and in the home page's FAQ section; both draw the same list with `components/home/FaqList`, and the footer and the phone More menu link to `/faq`.
- **Privacy policy:** `/privacy` shows `legal_privacy_html` from a new `legal` content section (`GET/PUT /content/legal`, `legal_%` keys, apart from home so it isn't sent with every page), falling back to the generated `PRIVACY_POLICY_HTML` until it's saved or if it can't load. It's edited at `/privacy-policy` (`src/admin/content-management/PrivacyPolicy.tsx`) with `cms/RichTextField.tsx` (a toolbar over a contentEditable area) and sanitized before saving. The Worker has no `legal` section, so before the Phase 3 cutover the editor can't load or save it.
- **Content editors** (Homepage, Services, Artists, About Us, Contact Us, FAQs, Terms, Privacy Policy) use `components/admin/cms/CmsEditor.tsx`: the controls in a side panel (`cms/fields.tsx`: `PanelSection`, `TextField`, `ImageField`, `SaveBar`) and the real public page in an iframe, at desktop width (scaled to fit) or in a phone frame; on phones, Edit and Preview tabs. Homepage, About and Contact are always-editable forms with Save/Discard, and the preview shows their unsaved changes live: the editor posts drafts to the frame, and inside it (`lib/cmsPreview.ts`, recognized by the frame's `name`) the public fetches (`previewed()` in the services) return the saved content with the drafts merged over it, while the public hooks fetch again on `usePreviewVersion()`. The list editors save each item on its own and send a refresh after every save. In the preview `useHome` doesn't send an admin to the dashboard.
- Screens and admin components are client components (`"use client"`), but they are still rendered on the server first, so `window`/`document`/DOMPurify can't run during render: use effects or `hooks/useIsClient`.
- `src/lib/router.tsx` re-creates the react-router API the screens use (`Link`, `useNavigate`, `useLocation`, `useParams`, `useSearchParams`, `Navigate`) on `next/navigation`. Router `state` is kept in sessionStorage per target path (cleared on a fresh page load, kept on reload) and is null during server render/hydration, so screens that need it on first render (booking, payment, reschedule, profile) are wrapped in `components/guards/ClientOnly` in their `page.tsx`. Screens using `useSearchParams` need a `<Suspense>` there too.
- With `NEXT_PUBLIC_API_BASE_URL=/api`, the browser stays same-origin. `/api` paths with a route file under `src/app/api/` are answered by Next; every other `/api` path reaches `API_PROXY_TARGET` (the live Worker) through the `fallback` rewrite in `next.config.ts`, so Vercel previews need no Worker CORS change.
- SVGs import as React components via `@svgr/webpack`; static image imports are `StaticImageData`, so use `.src`.

### API on Supabase (migration: Phase 3 cutover pending)
The Worker's endpoints are ported to route handlers in `src/app/api/` on Supabase Postgres. Until the Phase 3 data cutover the live data stays in D1, so the Worker remains the source of truth:
- **`API_BACKEND` switch:** ported handlers are wrapped in `ported()` (`src/server/worker.ts`). While `API_BACKEND` isn't `next` (the default, and production until cutover) they forward to the Worker unchanged. A route file's unported methods are `forwardToWorker` so writes still reach the Worker. Ported so far:
  - **2A:** GET `/content/[section]`, `/carousel`, `/faqs`, `/tacs`, `/categories`, `/services`, `/services/[id]`, `/services/[id]/gallery` and `/nailists`, plus POST/DELETE `/upload/image`.
  - **2B:** booking, appointments and payments (`/booking/*`, `/appointments/*`, `/payment/*`, `/settings/payment`).
  - **2C:** everything else: the CMS and catalog writes (content, carousel, FAQs, terms, categories, services, gallery, nailists with their services, time slots and days off), `/directory`, `/users/*` (profile, admins, promote-admin, stamps, QR scan, redeem, scan history), `/submit`, `/emails` and `/health`. Every Worker endpoint now has a route file; only unknown paths still fall back to the Worker.
  - **Artist gallery (new, no Worker equivalent):** GET and POST `/nailists/:id/gallery`, DELETE `/nailist-gallery/:id` (table `nailist_gallery`, migration `20261012000000_nailist_gallery.sql`). Shown on the public artist page `/artists/[id]`; the admin edits it in the Nail Artists screen. Until the table exists in a database, or while `API_BACKEND` isn't `next`, the gallery request fails and the page simply shows no gallery.
  - **Dashboard (new, no Worker equivalent):** GET `/dashboard?range=week|month|last30|last90|year`, admin only (table queries in `src/server/dashboard.ts`). While `API_BACKEND` isn't `next` the request is forwarded to the Worker, answered 404, and the screen shows its error state.
  - **Warm leads (new, no Worker equivalent):** GET `/leads`, admin only: the Clerk ids of client accounts that haven't booked (no confirmed or completed appointment) and were active (account made or booking started) in the last 60 days. The dashboard counts them under Needs attention; Clients & Bookings counts them in its stat cards (`components/admin/DirectoryStats.tsx`, counts in `src/lib/directoryStats.ts`) and shows just them at `/clients?view=leads`.
  - **Artist utilization (new, no Worker equivalent):** GET `/utilization?week=YYYY-MM-DD`, admin only (`src/server/utilization.ts`): for the Monday-to-Sunday week holding that date, each artist's active bookings per day against their time slots (none on a regular or one-off day off). Shown on the dashboard as a week grid with its own arrows.
  - **Client pages (new, no Worker equivalent):** GET `/clients/:id` (profile, summary, every appointment), `/clients/:id/notes` (GET, POST with an optional `appointment_id`), `/clients/:id/notes/:noteId` (PUT, DELETE) and `/clients/:id/next-steps` (GET, PUT), admin only, in `src/server/handlers/clients.ts`; tables from migration `20261014000000_client_notes.sql`. The admin page is `/clients/[id]` (`src/admin/front-desk/ClientPage.tsx`), opened from the dashboard's bookings table and sales record; the shared walk-in guest and admins have no page.
  - **Reviews (new, no Worker equivalent):** GET `/reviews` (the signed-in client's own) and POST `/reviews` (multipart: `appointment_id`, `rating` 1-5, `comment`, optional `file`), in `src/server/handlers/reviews.ts`; table `reviews`, one per appointment, migration `20261015000000_reviews.sql`. Only the client who booked can review, and only a completed visit; the photo goes to R2 under `reviews/` with the proof upload's limits. On the client's profile a completed visit's sheet shows the form or the review left (`components/profile/ReviewCard.tsx`, `hooks/useMyReviews.ts`, `services/reviewService.ts`), and its card says "Leave a review" until one is. Until the table exists, or while `API_BACKEND` isn't `next`, the list fails quietly and sending a review shows an error.
  - **Directory profiles (new, no Worker equivalent):** GET `/directory/profiles`, admin only (`src/server/handlers/directoryProfiles.ts`): each Clerk user's uploaded photo, join date and last sign-in by Clerk id, for the directory cards (`/directory` keeps the Worker's columns). A Clerk failure answers `{ profiles: {} }` and the cards show initials.
  - **Handlers:** the 2B and 2C handlers live in `src/server/handlers/`, and the route files under `src/app/api/` only map URLs, including the Worker's alias paths, to them.
- **Access rules (stricter than the Worker):** the ported routes don't copy the Worker's open access. Access comes from the verified session:
  - **Owner or admin:** appointment by id, payment details, payment create, reschedule and refund.
  - **Owner only:** proof upload, and reviewing a visit.
  - **Admin only:** the appointment list, status changes, admin booking, the schedule, proof review and the payment settings PUT. Also every CMS/catalog write (including `/gallery/:id`, which the Worker left open), the directory, the admin list and promote-admin, `/users/stamps`, `/users/scan/*` and the scan history.
  - **Signed-in user's own:** `/users/profile` and `/users/redeem` use the session's user, not the `clerk_id` param; `/users/appointments` and `/users/clerk/:id` are owner or admin.
  - **`/emails`:** answers `{ success: true }` without sending. The confirmation emails go out on the server when a payment is confirmed; the Worker's route emailed whatever it was sent.
  - **Booking create:** uses the session's user, not `user_id` from the body.
  - **Xendit webhook:** must carry `x-callback-token` equal to `XENDIT_CALLBACK_TOKEN`, or it's refused.
- **Emails** (`src/server/email.ts`) HTML-escape every value and are sent after the response with `after()` (`inBackground` in `src/server/http.ts`).
- **Server modules:** `src/server/` holds the server-only code (`import "server-only"`):
  - `db.ts`: postgres.js on `DATABASE_URL`, the Supabase transaction pooler, `prepare: false`. Connections can die silently (e.g. after a laptop sleep), leaving every query queued forever, so `ported()` checks a request still waiting after 10s with `sqlResponds()`: if the connections don't answer, `resetSql()` replaces the client (only the one found dead). Either way a GET runs once more (a single connection can die while the rest still work) and the first answer wins; a GET whose connection broke under it (`CONNECTION_DESTROYED` etc.) also runs once more. Writes are never re-run. These limits count working time, not wall time (`src/server/loopTimer.ts`): the dev server blocks its event loop while compiling routes or compacting its cache (20-50s), and plain timers then fired before the database answers already waiting were read, which looked like dead connections and set off needless resets. Connections live at most 60s. `resetSql()` gives the old connections a few seconds to close instead of cutting them at once: Supabase's pooler counts a connection cut during login as a failed login and, after several, refuses every new connection for about two minutes (`ECIRCUITBREAKER`). A stall also logs when the server itself was frozen for most of it, and the Schedule asks once more after a 503. A stalled request also logs the database's own activity (`logDatabaseActivity`, over a separate one-off connection) to show whether it was busy, blocked on a lock, or not reached at all. The Clerk directory sync (`syncAllUsersFromClerk`, started by every `GET /directory`) runs one at a time and at most every two minutes. Anything unanswered at 30s gets a 503. Values go in as template parameters. Without prepared statements, array parameters aren't typed, so build `OR` fragments instead.
  - `auth.ts`: the Clerk-verified requester, with roles from `users.role`. The `clerk_id` header is never trusted.
  - `r2.ts`: R2 through the S3 API.
  - `catalog.ts`: the read queries.
  - `clerkSync.ts`: directory sync with Clerk (names, `publicMetadata.role`, deletes). Clerk errors are logged, never fail the request.
- **Response parity:** responses must match the Worker's exactly (columns, order, number types; cast `count(*)` to `int`).
- **Schema and seed:** the schema is in `supabase/migrations/` and is the D1 schema translated: same columns, 0/1 integer flags, text dates and times, RLS on with no policies. Schema changes are new files in `supabase/migrations/`. `supabase/seed.sql` is dev/test data, edited by hand (its old generator read the removed `database/init.sql`); never load it into production.
- **Tests:** `npm run test:db` runs `src/tests/db` against a throwaway Docker Postgres. The files run one at a time, since each rebuilds the schema through `testDatabase.ts`. Plain `npm test` skips those tests.
